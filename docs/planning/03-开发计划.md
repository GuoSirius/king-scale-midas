# 03 · 开发计划

> 分 7 个阶段，每阶段都有可验收的交付物。
> 工作量档位：**S** = 小（半天内）｜**M** = 中（1–2 天）｜**L** = 大（3–5 天）

---

## ⚠️ 排期的第一原则：数据管道必须最先上线

这不是常规的「先搭架子再做功能」。这个项目有个特殊性：

> **涨停数据是时间序列，今天没采集，这一天就永远缺失了。**
> 行情价格可以事后补（历史 K 线接口随时能查），但**「涨停原因」几乎无法追溯** ——
> 问财、开盘啦这些源只提供当日或近几日的涨停原因，超过一周就查不到了。

所以计划的排序是反直觉的：

```
Phase 1（数据管道）→ 先跑起来，哪怕前端还是一片空白
                     ↓
   同时进行：Phase 2/3/4 的界面开发
                     ↓
   等你做完界面，数据库里已经躺着一两个月的完整数据了
```

**建议：Phase 0 + Phase 1 在第一周内完成并每日运行，剩下的慢慢做。**

## Phase 0 · 项目奠基 `S`

### 任务
- [ ] `pnpm dlx nuxi@latest init`，Nuxt 4，Node 24，pnpm 10
- [ ] 接入 UnoCSS（`preset-wind4` + `preset-icons` + `preset-typography`）

- [ ] 目录约定：`app/` `server/` `shared/`，配好路径别名
- [ ] `shared/schemas/` 放 zod 校验，前后端共用
- [ ] 建 Cloudflare 账号，`wrangler login`，创建 D1（preview + production）、KV、R2
- [ ] `nitro-cloudflare-dev` 打通本地绑定
- [ ] 配好 `routeRules`（SSR/ISR/SSG 全部预留位置，见文档 01）

### 验收
本地 `pnpm dev` 能跑，页面能读到 D1 里的一张测试表，`pnpm build && wrangler deploy` 能部署成功。

## Phase 1 · 数据管道（最高优先级）`L`

### 1.1 数据库骨架 `M`
- [ ] Drizzle schema：先建 B 域（`stocks` `industries` `concepts` `trade_calendar`）+ C 域（`limit_records` 等）
- [ ] `drizzle-kit generate` 生成迁移，`wrangler d1 migrations apply` 落库
- [ ] 灌基础数据：全市场股票列表、行业树、概念板块、当年交易日历
- [ ] 写 seed 脚本，本地/preview/production 三套环境都能一键初始化

### 1.2 Python 采集器 `M`
独立目录 `collector/`（或独立仓库），不进 Nuxt 构建。

- [ ] `stock_zt_pool_em` → 涨停池
- [ ] `stock_zt_pool_dtgc_em` → 跌停池
- [ ] `stock_zt_pool_zbgc_em` → 炸板池
- [ ] `stock_zt_pool_strong_em` → 强势股池
- [ ] pywencai → 涨停原因（Cookie 存环境变量，失效时降级不阻塞主流程）
- [ ] 清洗层：字段映射、单位统一（万元→元）、连板数解析、题材别名归一化
- [ ] 输出标准 JSON + HMAC 签名 POST 到 `/api/ingest/*`
- [ ] 失败重试（指数退避）+ 部分成功上报
- [ ] 本地 `.env` 配置，支持 `--date` 参数补跑历史

### 1.3 Ingest 接口 `M`
- [ ] `POST /api/ingest/limit-records`：HMAC 校验 + 时间戳防重放 + zod 校验
- [ ] 幂等 upsert，`WHERE is_verified = 0` 保护人工数据
- [ ] `db.batch()` 批量写入
- [ ] 原始 JSON 存 R2，key = `raw/{date}/{jobType}-{batchId}.json`
- [ ] `ingest_jobs` 全程记录状态
- [ ] `POST /api/ingest/summary`：聚合生成 `market_daily_summary` 和 `concept_daily_stats`

### 1.4 调度与监控 `S`
- [ ] GitHub Actions cron：`30 7 * * 1-5`（UTC，对应北京时间 15:30）
- [ ] 采集失败 → 推送通知（企业微信/飞书/Telegram 机器人）
- [ ] Cloudflare Cron Trigger 做兜底检查：18:00 检查当日数据是否到齐，缺了就告警

### 验收
连续 3 个交易日自动采集成功，`limit_records` 有完整数据，`ingest_jobs` 状态正常，人为让接口失败能收到告警。

## Phase 2 · 认证与权限 `L`

### 2.1 基础认证 `M`
- [ ] A 域全部表 + seed 内置角色与权限点
- [ ] `nuxt-auth-utils` 接入，sealed session cookie
- [ ] 密码哈希用 **Web Crypto PBKDF2**（Workers 上 bcrypt/argon2 不可用！）
- [ ] 注册：zod 校验 + Turnstile 验证码 + 默认 `status = 'pending'`
- [ ] 登录：状态机判断，pending/rejected/suspended 各返回明确文案
- [ ] 失败计数 + 锁定（KV 存计数器，5 次锁 15 分钟）
- [ ] 登出、改密码、找回密码

### 2.2 RBAC `M`
- [ ] 权限点常量集中定义在 `shared/permissions.ts`
- [ ] 登录时算出权限集合 → 写入 session（避免每请求查库）
- [ ] `server/middleware/auth.ts`：统一鉴权入口，路由级权限映射表
- [ ] `app/middleware/auth.global.ts`：客户端守卫
- [ ] `usePermission()` composable + `<Can>` 组件
- [ ] 全量审计日志

### 2.3 管理员后台 `M`
- [ ] `/admin` 走 `ssr: false`（SPA 模式，省 Workers CPU）
- [ ] 待审用户列表 → 通过（同时授予角色）/ 拒绝（填原因）
- [ ] 用户列表：搜索、状态筛选、改角色、封禁/解封
- [ ] **不能操作同级或更高 level 的用户**（防止管理员互删）
- [ ] 角色权限矩阵配置界面
- [ ] 审计日志查询
- [ ] 采集任务监控面板（读 `ingest_jobs`）

### 验收
新用户注册后无法登录 → 管理员审核通过 → 能登录且权限正确 → 越权访问 `/api/admin/*` 返回 403 → 所有操作在审计日志可查。

## Phase 4 · 人工编辑与复盘 `M`

## 关键风险与应对

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| 问财 Cookie 失效 / 接口改版 | 高 | 涨停原因断供 | 多源并行（问财 + 开盘啦 + 东财）；原因缺失不阻塞主数据；人工兜底 |
| Workers 免费版 CPU 超限 | 高 | SSR 页面 500 | 升级 Paid（$5/月）；或激进使用 ISR |
| CF 国内访问慢 | 中 | 体验差 | 预留 `preset: node-server`，可随时搬到国内服务器 |
| AKShare 接口变更 | 中 | 采集失败 | 锁定版本 + 字段映射层集中管理 + 告警 |
| 数据源反爬限流 | 中 | 采集失败 | 请求间隔 ≥ 2s、随机 UA、失败重试、多源冗余 |
| D1 免费额度超限 | 低 | 服务不可用 | 派生表 + 索引优化（已在设计中规避）；监控 rows read |
| 合规风险 | 低 | — | 明确免责声明、数据来源署名、不提供投资建议、不做荐股 |

## 立即可以做的第一步

如果你确认这个方案，第一天的具体动作是：

1. 注册 Cloudflare 账号，创建 D1 数据库（5 分钟）
2. `pnpm dlx nuxi@latest init` 初始化项目，接 UnoCSS（30 分钟）
3. 把文档 02 的 schema 落成 Drizzle 文件，跑第一次迁移（1 小时）
4. 写 Python 采集器抓今天的涨停池，手动 POST 一次（2 小时）
5. 配 GitHub Actions cron，让它明天 15:30 自己跑

**第一天结束时，数据就开始积累了。** 界面可以慢慢磨，数据一天都不能等。
