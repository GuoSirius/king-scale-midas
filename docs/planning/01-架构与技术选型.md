## 一、先说三个「必须先决策」的硬约束

在写一行代码之前，这三件事会直接决定架构走向。我把它们放最前面，因为它们是这个项目最容易踩的坑。

### 🔴 硬约束 1：Cloudflare Workers 跑不了 Python，而 A 股最好的免费数据源全是 Python

Cloudflare Workers 是 V8 isolate 运行时（workerd），不是 Node、更不是 Python。而 A 股涨跌停数据质量最高的免费方案是：

| 库 | 语言 | 能力 | 是否能跑在 CF Workers |
|---|---|---|---|
| AKShare | Python | 涨停池 / 跌停池 / 炸板池 / 强势股池 / 龙虎榜 / 资金流 | ❌ |
| pywencai（同花顺问财） | Python + Node | **涨停原因**、题材标签 | ❌ |
| 开盘啦逆向接口 | Python/任意 | 涨停原因板块、连板梯队、情绪 | ⚠️ 理论可以，但需自己实现 |
| 东方财富 push2 HTTP 接口 | 任意 | 涨停池原始 JSON | ✅ 可以 fetch |

**结论：采集层必须和 Web 应用物理分离。**
这不是妥协，反而是更好的架构 —— 换数据源不动前端，采集失败不影响站点可用。

### 🔴 硬约束 2：Cloudflare Workers **免费版单请求 CPU 上限 10ms**，Nuxt SSR 很容易超

一个中等复杂度的 Vue 页面服务端渲染，CPU 时间通常在 15–60ms。免费版会直接抛 `Exceeded CPU time limit`。

**建议：Workers Paid（$5/月，CPU 上限 30s）**。这 5 美元是这个项目最值的一笔开销。
如果坚持白嫖免费版，就必须把绝大多数页面做成 ISR/预渲染，SSR 只留给登录后的动态页 —— 能做，但很别扭。

### 🟡 硬约束 3：Cloudflare 在中国大陆的访问质量

你的用户 100% 在国内。CF 免费版国内访问经常绕道美西/新加坡，延迟 200–500ms，晚高峰更差。

三条路，按体验排序：

| 方案 | 国内体验 | 成本 | 备案 |
|---|---|---|---|
| 国内云服务器（阿里/腾讯轻量） | ⭐⭐⭐⭐⭐ | ￥60–100/月 | 需要 |
| Cloudflare Workers Paid | ⭐⭐⭐ | $5/月 | 不需要 |
| CF 免费版 | ⭐⭐ | 0 | 不需要 |

**好消息**：Nitro 的 preset 机制让你可以「先 CF、不爽再搬到国内 Node 服务器」，代码一行不改，只改 `nitro.preset`。所以这个决定可以推迟，但数据库选型不能推迟（见下）。

| 依赖 | 说明 |
|---|---|

**为什么是 Drizzle 不是 Prisma**：Prisma 在 Workers 上需要 driver adapter + 体积大，冷启动慢；Drizzle 编译期生成 SQL，产物极小，和 D1 是天作之合。

| 依赖 | 说明 |
|---|---|

| `@node-rs/argon2` 或 Web Crypto PBKDF2 | ⚠️ Workers 上 argon2 原生模块不可用，**必须用 Web Crypto 的 PBKDF2 或 scrypt**（见下方注意事项） |
| 自研 RBAC 中间件 | 角色 → 权限点，服务端 + 客户端双重校验 |

> ⚠️ **密码哈希坑**：`bcrypt` / `argon2` 都是原生模块，在 Cloudflare Workers 里跑不了。
> 方案：用 Web Crypto API 的 `PBKDF2`（迭代 100k+，SHA-256），跨运行时通用。
> 如果后期迁到 Node 服务器，可以平滑升级到 argon2id 并做惰性 rehash。

### PWA
| 依赖 | 说明 |
|---|---|
| `@vite-pwa/nuxt` | Nuxt 官方推荐，基于 Workbox |

PWA 策略（针对 SSR 场景要小心）：
- **HTML 文档**：`NetworkFirst` + 3s 超时兜底，绝不能用 CacheFirst（否则用户永远看到昨天的涨停）

- **API 数据 (`/api/records/**`)**：`StaleWhileRevalidate` + 自定义过期（历史日期数据可缓存 7 天，当日数据 5 分钟）
- **离线页**：预缓存一个 `offline.vue`，断网时展示最后一次同步的日期
- 安装横幅 + iOS `apple-touch-icon` + `maskable` 图标齐全

## 四、渲染策略：SSR 为主，为 CSR / SSG / ISR 预留

Nuxt 的 `routeRules` 是路由级的，你现在写好，将来改一行配置就能切换渲染模式，**不需要重构代码**。这正好满足你「后期可能加 CSR+SSG+ISR」的要求。

```ts
// nuxt.config.ts
export default defineNuxtConfig({
  ssr: true,                       // 全局默认 SSR

  routeRules: {
    // 【SSG · 预渲染】纯静态内容，构建时生成
    '/':               { prerender: true },
    '/about':          { prerender: true },
    '/docs/**':        { prerender: true },

    // 【ISR】历史复盘页 —— 数据永不变，首次访问生成后长期缓存
    '/daily/**':       { isr: 60 * 60 * 24 * 30 },

    // 【ISR 短周期】排行榜/统计页 —— 盘后每天变一次
    '/rank/**':        { isr: 60 * 10 },
    '/sector/**':      { isr: 60 * 10 },

    // 【SSR】登录态相关，实时渲染不缓存
    '/dashboard/**':   { ssr: true },
    '/notes/**':       { ssr: true },

    // 【CSR / SPA】后台管理 —— 交互密集、SEO 无意义，关掉 SSR 省 CPU
    '/admin/**':       { ssr: false, robots: false },

    // 【API 缓存】公开只读接口走边缘缓存
    '/api/public/**':  { cache: { maxAge: 60, swr: true } },
    '/api/ingest/**':  { cache: false, robots: false },
  },

  nitro: {
    preset: 'cloudflare_module',   // 想搬回国内服务器？改成 'node-server' 即可
    prerender: { crawlLinks: true, routes: ['/', '/sitemap.xml'] },
  },
})
```

**关键提醒**：Cloudflare 上的 ISR 依赖 Cache API + KV。要在 `wrangler.jsonc` 里绑定一个 KV namespace 给 Nitro 缓存用，否则 ISR 退化成普通 SSR。

## 五、数据源方案（含「涨停原因」的真相）

### 5.1 各字段的实际来源

| 你要的字段 | 数据源 | 接口 | 可靠度 |
|---|---|---|---|
| 股票代码/名称 | AKShare | `stock_zt_pool_em` | ⭐⭐⭐⭐⭐ |
| 涨停/跌停/炸板 | AKShare | `stock_zt_pool_em` / `stock_zt_pool_dtgc_em` / `stock_zt_pool_zbgc_em` | ⭐⭐⭐⭐⭐ |
| 连板数、封板资金、首末封板时间、炸板次数 | AKShare | 同上（涨停池自带） | ⭐⭐⭐⭐⭐ |
| **所属行业** | AKShare | 涨停池自带「所属行业」字段（东财行业） | ⭐⭐⭐⭐ |
| **所属板块/概念题材** | AKShare | `stock_board_concept_name_em` + 成分股 | ⭐⭐⭐⭐ |
| **涨停原因** | ⚠️ 见下 | — | ⭐⭐⭐ |

### 5.2 关于「涨停原因」——必须提前说清楚

**东财涨停池接口里没有「涨停原因」这个字段。** 市面上所有带涨停原因的产品，数据来源无外乎这几个，全都是非官方接口：

| 来源 | 获取方式 | 优点 | 风险 |
|---|---|---|---|
| **同花顺问财** | `pywencai` 库，查询「今日涨停 涨停原因」 | 质量最好、有原因短语 | 需 Cookie，会过期；限流；非官方接口随时可变 |
| **开盘啦 (KaiPanLa)** | 逆向 APP 接口 | 有「涨停原因板块」+ 连板梯队 | 完全非官方，稳定性靠运气 |
| **财联社电报** | AKShare `stock_zh_a_alerts_cls` | 官方新闻源，合规 | 需自己做「新闻 → 股票」归因，非结构化 |
| **东方财富「涨停揭秘」** | 网页解析 | 免费 | 需维护解析规则 |

**我的建议（也正好呼应你需求 6 里的"自定义新增"）：**

> 采用「**机器初筛 + 人工定稿**」的两级模型。
>
> 1. 采集器自动抓取问财/开盘啦的原因，写入 `reason_raw`（原始）字段，标记 `source = 'wencai'`、`is_verified = 0`
> 2. 你在后台复盘时，一键确认或改写，写入 `reason_final`，标记 `is_verified = 1`、`edited_by = 你的 userId`
> 3. 数据库保留两个字段 + 修改历史，谁改的、改了什么、什么时候改的，全部可追溯

这样即使某天问财接口挂了，你的历史数据依然完整，且人工校订过的数据是你这个系统真正的护城河 —— 这是市面上免费产品给不了的。

### 5.3 采集器部署方案对比

| 方案 | 稳定性 | 成本 | 能否拿涨停原因 | 建议 |
|---|---|---|---|---|
| **A. GitHub Actions cron** | ⭐⭐⭐ 海外 IP，东财偶发超时；cron 有 5–15 分钟延迟 | 免费 | ⚠️ 问财对海外 IP 较敏感 | MVP 起步用 |
| **B. 国内轻量服务器 / NAS / 常开电脑** | ⭐⭐⭐⭐⭐ | ￥0–60/月 | ✅ | **长期主力，强烈推荐** |
| **C. CF Cron Trigger 直连东财** | ⭐⭐⭐ | 免费 | ❌ | 做行情兜底 |

**最终推荐：B 为主，A 为备（B 失败 2 小时后自动接管），C 兜底核心行情。**
三者写的是同一个 `/api/ingest` 幂等接口，谁先成功谁生效，后到的不覆盖已人工校订的数据。

### 5.4 Ingest 接口设计要点

```
POST /api/ingest/limit-records
Headers:
  X-Ingest-Timestamp: 1754054400        # 时间戳，超过 5 分钟拒绝（防重放）
  X-Ingest-Signature: sha256=xxxx       # HMAC-SHA256(body + timestamp, INGEST_SECRET)
  X-Ingest-Source: akshare-github-actions

Body: { tradeDate: "2026-08-01", limitType: "up", records: [...], meta: {...} }
```

- **幂等**：`ON CONFLICT (trade_date, stock_code, limit_type) DO UPDATE`
- **保护人工数据**：`WHERE is_verified = 0` —— 已人工确认的记录，机器不许覆盖
- **批量写入**：D1 用 `db.batch()` 一次提交，减少往返（一天约 100–300 行，毫无压力）
- **原始快照**：整包 JSON 存 R2，出问题可重放清洗，不占 D1 空间

## 六、认证 · 授权 · 管理员审核流程

### 用户状态机

```
  注册提交
     │
     ▼
 [pending] ──管理员通过──▶ [active] ──违规──▶ [suspended]
     │                        │                    │
     └──管理员拒绝──▶ [rejected]                   └──解封──▶ [active]
                                                   
 [active] ──长期不登录/主动注销──▶ [disabled]
```

- 注册后 `status = 'pending'`，登录接口直接拒绝并返回明确文案「账号审核中」
- 管理员后台看到待审列表，可通过/拒绝（拒绝需填原因，写入审计日志）
- 审核结果邮件通知（可选，用 Resend / 阿里云邮件推送；Workers 上不能用 SMTP，必须用 HTTP API 的邮件服务）

### RBAC 模型

采用 **角色 → 权限点** 的经典模型，不搞过度设计的 ABAC：

| 角色 | 权限 |
|---|---|
| `super_admin` | 全部 + 用户管理 + 系统设置 |
| `admin` | 用户审核 + 数据编辑 + 查看审计日志 |
| `editor` | 涨停原因校订、笔记、标签管理 |
| `member` | 查看全部数据、导出、自己的笔记与自选 |
| `guest` | 只看最近 N 天的公开数据（用于对外展示/引流） |

权限点命名：`resource:action`，如 `record:edit`、`user:approve`、`data:export`。

**三层防护，缺一不可**：
1. `server/middleware/auth.ts` —— 服务端统一拦截（真正的安全边界）
2. `app/middleware/auth.global.ts` —— 客户端路由守卫（体验层，防止闪现）
3. 组件级 `v-if="can('record:edit')"` —— UI 层隐藏

> 客户端的一切校验都只是「体验」，服务端校验才是「安全」。所有 `/api/admin/**` 必须在服务端逐个校验权限，不能只靠路由前缀。

### 安全细节
- 登录失败计数 + 指数退避锁定（存 KV，5 次失败锁 15 分钟）
- 注册加 Cloudflare Turnstile（免费的验证码替代品，比 reCAPTCHA 国内可用）
- Session cookie：`httpOnly` + `secure` + `sameSite: lax`，7 天有效、滑动续期
- 敏感操作（改密码、改权限）二次验证
- 全量审计日志，含 IP、UA、操作前后的值 diff

## 七、响应式：PC 与移动端

**不做两套代码，做一套自适应 + 关键组件分形态渲染。**

| 断点 | 宽度 | 布局 |
|---|---|---|
| `xs` | < 640px | 单列卡片流，底部 Tab 导航，表格降级为卡片 |
| `sm/md` | 640–1024px | 双列，抽屉式侧栏 |
| `lg+` | > 1024px | 固定左侧栏 + 主区 + 可选右侧详情面板 |

关键取舍：
- **涨停表格在移动端不是表格**。50+ 只股票 × 12 列，横向滚动是灾难。移动端渲染为「卡片列表 + 折叠详情」，用同一份数据、不同的展示组件（`<LimitTable>` / `<LimitCardList>`，靠 `useBreakpoints` 切换）。
- 移动端优先做「今日速览」：涨停家数、最高连板、赚钱效应三个大数字 + 题材热力榜，这是复盘时手机上最想看的。
- 虚拟滚动（`@tanstack/vue-virtual`）应对连板天梯的长列表。
- 触摸手势：左右滑动切换交易日。
